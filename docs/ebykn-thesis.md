# Ebykn：思想

Ebykn（エビケン、イービーワイケーエヌ、読みは自由）は、Rust にトランスパイルし Verus で検証する言語と、そのエコシステムの構想である。この文書は、なぜ作るのか、何を保証し何を保証しないのか、何が新しく何が借り物なのかを述べる。言語仕様は `ebykn-spec.md`。

---

## 1. ステートメント

### 一文
> 信頼しているライブラリが自称する性質を前提に、自分が書いた部分だけを、選んだ性質について証明する。その前提を TypeScript の型定義のように共有し、増やし、直していくエコシステムを、言語と一体で作る。

### 全文
形式検証はこれまで、人命や資産に関わるシステムを対象に、プログラム全体の正しさを証明することを目標としてきた。だが大半のソフトウェアはそこまでを必要としない。開発者は標準ライブラリや広く使われるライブラリを信頼し、自分が書いた部分だけをテストで確かめてきた。

LLM が証明を書く労力を下げつつある今、この「信頼の上に自分の部分を確かめる」という日常の実践を、テストから証明へ引き上げられる。依存するライブラリが自称する性質を前提として受け入れ、その前提の下で、自分が書いた範囲が選んだ性質を満たし、未定義動作を起こさないことを証明する。全体の健全性は求めない。前提が間違っていれば結論も間違う、という条件付きの保証で十分に有用である。

この実践には、性質の宣言と検証結果を共有するエコシステムが要る。TypeScript が `.d.ts` でライブラリに型を自称させ、それを共有することで型の恩恵を漸進的に広めたように、ライブラリに性質を自称させる性質ファイルを共有する。性質ファイルは証明されていなくてよい。使われ、読まれ、間違いが見つかれば直される。共有される性質が増えるほど、自分のコードに性質を書くことは容易になる。

この条件付き検証と性質の共有を一級に扱う言語とエコシステムを作り、形式検証を日常のプログラミングの道具にしたい。

## 2. 保証するもの、しないもの

**保証文**：`unchecked` の印が付いた主張（自分のコードの検証しない部分、性質ファイルの宣言、公理）がすべて正しければ、verified なコードは未定義動作を起こさず、宣言した契約を満たす。

| 保証しない | 理由 |
| --- | --- |
| `unchecked` の主張が正しいこと | 前提として受け入れる。TypeScript の `.d.ts` が実装の型を保証しないのと同じ |
| プログラム全体の健全性 | 目的にしない。全ての依存に証明を付けることは現実的でなく、付けないことを理由に既存資産を捨てることもしない |
| 証明がない箇所の実行時の挙動 | 「証明がなければ何が起きても知らない」で揃える。実行時検査は挿入しない |

状態はツールが表示する：**verified**（本体の証明が通り、依存する契約が全て verified か `unchecked`）、**unverified**（未完成、または依存先に unverified がある）、**unchecked**（主張のみ）。`ebykn status` が、自分の結論が何を前提にしているかを一覧にする。これは監査のためではなく、次に証明する場所の地図である。

## 3. 三本の柱

### 柱 1：テストと全体検証の間の空白を、正直な保証文で埋める
形式手法の採用は二極化している。安全クリティカルな少数が全体を証明し、残りは何もしない。Google の Reid らは開発者の 1% 未満しか形式検証を使っておらず、「正しさは重要だ」と説くのではなく開発者の既存の実践に統合して週単位で正の費用対効果を出すべきだと述べた（HATRA 2020）。産業の形式手法でも、AdaCore と Thales の SPARK 採用指針は Stone から Platinum までの段階を置き、完全な機能的正しさは最上位の一部にだけ適用する。「前提が正しければ、自分の範囲は契約を満たし UB を起こさない」は、この空白に置ける明確で正直な保証である。

### 柱 2：暗黙の信頼を、明示された前提に変える
誰もコンパイラ・OS・libc を検証しない。全員が条件付きで仕事をしているが、条件は書かれていない。性質ファイルは「このライブラリについて皆が仮定していること」を機械可読に書き出す。仮定が diff でき、レビューでき、共有できる。分野の暗黙知が明文化される。

### 柱 3：AI がコードを書く時代に、人間が読むものは仕様になる
証明を AI が書けるようになれば形式検証の経済が変わり、課題は仕様を正しく定めることに移る（Kleppmann 2025、de Moura 2026）。Ebykn は、仕様は人が読み、証明は AI が書き、証明フェーズは仕様と実装を変えられない、という分担を言語の構造にする。性質ファイルの共有は、仕様を書く費用を分担する仕組みである。

## 4. 言語が引き受ける三つのこと

| # | 何を | なぜ Verus のままでは足りないか |
| --- | --- | --- |
| C1 | 権限（permission）を第一級の構文で書く。`unsafe` なしで連結リスト・グラフ・内部可変性を書き、検証されれば UB がない | Verus では権限トークンを `Tracked<PointsTo<T>>` として引数で持ち回り、読み書きが関数呼び出しになる |
| C2 | 実装・契約（人が読む）と証明（AI が書く）を分離する。ソースファイルには証明が書けない。証明フェーズでソースが変わっていないことを機械的に検査する | 同一ファイルに混在する |
| C3 | 性質ファイルを一級の成果物にし、合成・配布・状態の表示を行う | `assume_specification` はあるが、同一関数への重複宣言ができず、共有・解決・版対応の仕組みがない |

C1 が言語を要求し、C2・C3 はその言語に乗る。言語は Verus ツールチェーンの上の構文フロントエンドとして実装し、型・借用・名前解決・証明は rustc と Verus に任せる。新しい検証理論は作らない。

## 5. 先行するものと、新しいもの

| 要素 | 先例 |
| --- | --- |
| 条件付き・部分的な検証 | 全ての演繹的検証器の extern spec（Verus `assume_specification`、Creusot / Prusti / Flux `extern_spec`、Liquid Haskell `assume`）、SPARK の段階、Infer の continuous reasoning（O'Hearn 2018） |
| 意図的な不健全さを引き受ける | 「In Defense of Soundiness」（Livshits ら、CACM 2015）、ESC/Java、TypeScript（Bierman ら、ECOOP 2014） |
| 他人のライブラリへの外付け仕様 | Code Contracts の contract reference assembly、Liquid Haskell の `liquid-*` パッケージ、OpenJML の JDK 仕様、vstd `std_specs`、verify-rust-std |
| 任意の注釈・消去・漸進的導入 | Bracha「Pluggable Type Systems」、DefinitelyTyped、typeshed |
| 権限とデータの分離 | L3、Alias Types、Mezzo（`x @ t`、adoption and abandon）、GhostCell、Verus |
| 仕様と証明の分離 | Move Prover の `.spec.move`、MoonBit の `.mbt` / `.mbtp`、Why3 のセッション |
| AI が証明を書く | AutoVerus、vericoding ベンチマーク、Lean FRO |

新しいのは組み合わせの一つの列だけである：**第三者が書いて共有する、自称でよい性質の公共財**。Code Contracts と Liquid Haskell は近い機構を持っていたが、前者は非検証者への価値が null 検査しかなく型に吸収されて消え、後者は配布機構（wrapper パッケージ）の煩雑さで撤回された。思想が反証されたのではなく、労働コストと配布の問題だった。LLM が前者を、Rust の所有権（フレーム条件が要らない）と `assume_specification` 型の外付け（対象を包まない）が後者を変える。

## 6. 弱点（正直に）

| 弱点 | 答え |
| --- | --- |
| 自分の仕様を書くのは依然として難しい | 部分的でよい（選んだ性質だけ）。共有される定義・モデル・補題が語彙を安くする |
| 自称の性質が間違っていても何も壊れない（検出ループの不在） | 多くの人が依存する性質は読まれ、指摘される。ロングテールは品質が低いまま残るが、TypeScript も同じ条件で成功した。仕様が人に読める形であること（C2）が、この検出の前提 |
| TypeScript の `any` に当たる逃げ道（弱すぎる契約） | 証明フェーズが契約を変えられない構造（C2）と、`status` の表示 |
| 検証する人が少ないうちは公共財が立ち上がらない | 言語の普及は目標ではない。思想と、それが動く一つの実例を示すことが目標 |

## 7. 対象と非対象

**対象**：Rust の資産をそのまま使う普通のアプリケーションとライブラリ。重要な部分から証明を足していく。Rust で `unsafe` が要った構造を `unsafe` なしで書く。

**非対象**：全体の健全性。新しい検証理論。独自ランタイム・独自 ABI。Rust から呼べる API を設計で保証すること（出力の Rust は成果物であって API ではない。Ebykn で書けばよい）。言語を広めること（思想を提示するための最小の実装でよい。同じ思想のより良い言語が他所から出てくれば、それでよい）。

## 8. 名前

Ebykn。日本語の「エビやカニ」（Rust の甲殻類のイメージ）から。「えびやかに」と書くと「えびやか」という形容動詞があるかのように見える言葉遊びが由来だが、これは裏設定で、表向きの読みは自由。硬質な頭字語のように見えて由来は言葉遊び、というのが面白みである。拡張子は `.eyk`（source）と `.eykp`（proof）。
