# Ebykn 設計ノート：目的・判断基準・決定の記録・却下した案

版：2026-11-09
対象読者：言語の設計と実装を引き継ぐ人と AI。`ebykn-thesis.md`（思想）と `ebykn-spec.md`（実装仕様）を補う。仕様書は「何を作るか」だけを書く。本書は「なぜそうなったか」「迷ったらどう決めるか」「何を提案してはいけないか」を書く。仕様書と矛盾したら仕様書を優先し、矛盾を `OPEN.md` に記録する。

---

## 1. 作者が作りたいもの

### 1.1 目的の順序
1. **思想を提示すること。** 「信頼しているライブラリの自称する性質を前提に、自分の書いた部分だけを選んだ性質について証明する。その前提を共有するエコシステムを作る」。これを、動く一つの実例とともに示す。
2. **作者自身が趣味のプロジェクトで使えること。** 普通の Rust アプリケーションを Ebykn で書き、重要な部分に性質を付けられる程度の実用性。
3. 言語の普及は**目標ではない**。同じ思想のより良い言語が大きな組織から出てくれば、それで目的は達成される。言語を広めるために思想を弱めてはならない。

### 1.2 作りたいプログラム
| 用途 | 何を確かめたいか |
| --- | --- |
| glTF の読み込み → 有効性検証（添字が範囲内、NaN / inf を含まない）→ ポリゴン削減 → rayon で並列化 | 構造的性質（添字の有効性、三角形数、並列版が逐次版と同じ結果）。数値の有限性は検査関数（NaN / inf の三角形を取り除く）＋部分集合型 `FiniteMesh` で保証する。浮動小数点演算の性質は Verus では証明できないので求めない |
| 双方向リスト、親ポインタ付き木、グラフ・アリーナ（相互参照・循環参照） | `unsafe` なしで書け、検証されれば UB がない。O(1) の中間削除のように `unsafe` か添字アリーナでしか書けなかったものを素直に書く |
| `Rc<RefCell<T>>` の置き換え | 実行時の借用検査と panic を、静的な権限の義務に置き換える |
| 既存 Rust クレート（rayon、serde、std）を前提付きで使う | 性質ファイル |

自己参照構造体（自分のフィールドを指す。`Pin` 相当）は対象外。

### 1.3 実用性の基準
- Verus をそのまま使うより読みやすいこと。特に (a) 権限の読み書きが `*p` で書けること、(b) ソースに証明が混ざらないこと。
- Rust のコードがほぼそのまま貼れること（新構文は十数個）。
- 検証なしでもビルドできること。
- 証明は多くの場合 LLM が書く。人間はソース（実装と契約）だけを読む。

| 決めるべき事項を洗い出して提示する | 各決定に「何を決めるか・なぜ要るか・採ると何が変わるか・各案の利点欠点・推奨」を付ける |

## 3. 判断基準（迷ったときの優先順位）

### 3.1 設計の公理（順序付き。衝突したら先のものを優先）
| # | 公理 | 内容 |
| --- | --- | --- |
| A1 | 条件付きの正しさ | 保証するのは「`unchecked` が主張どおりなら、それ以外は UB を起こさず契約を満たす」だけ。全体の健全性や `unchecked` の検査は求めない |
| A2 | Rust と同じ意味、同じ速さ | 所有権・借用・型の意味は Rust。証明は実行時に何も残さない。証明がないからといって実行時検査を足さない |
| A3 | 部分的に使える | 一つの関数、一つの性質から始められる。未証明があってもビルドできる |
| A4 | 一つの言語、一つの逃げ道 | 検証しない場所の印は `unchecked` だけ。安全度の層を作らない |
| A5 | 読む回数は書く回数より多い | 書くのは多くが AI、読むのは人間。構文は読む側に最適化する。隠れた制御フロー・暗黙の変換を作らない |
| A6 | 処理系が薄い | 型・借用・名前解決・証明は rustc / Verus に任せる。Ebykn の規則は宣言と字句的スコープだけで決まる |
| A7 | 確立した語 | 先例で過半が一致する語を使い、造語は明記する |
| A8 | 機能は全員一致で入れる | 入れない決断を記録する |

### 3.2 個別の判断基準
| 迷い | 基準 |
| --- | --- |
| 新しい構文を足すか | 足さない。Rust の構文で書けるなら Rust の形。足すなら §15 の一覧（仕様書）に加え、造語なら印を付ける |
| 記号を足すか | 足さない。`@` 一つ。`@` は「仕様の世界（実行時に存在しないもの）」の印にだけ使う |
| 同じ概念を複数の形で書けるようにするか | しない（`and { }` と `&&` は改行の都合の例外で、意味は同じ） |
| 違う概念を同じ形で書くか | しない（実行時フィールド `self.x` と消去フィールド `self@x`、権限 `owns` と抽象状態 `spec`、`assert!` と `assert`） |
| ソースと証明のどちらに置くか | **意味または証明義務を変えるもの**（契約、資源の操作、`spec` フィールドの更新、ループ不変条件）はソース。**義務を解消するだけのもの**（`assert`、補題、トリガ、証明器の指示、証明専用の定義）は証明。ループ不変条件は両方に書けるが、証明側は追加だけ |
| 規則に型情報が要るか | 要るなら段階 1 には入れない。宣言（署名・`owns`・`let` の型注釈）と字句的スコープだけで決める。曖昧なら Rust のまま残して Verus にエラーを出させる |
| Verus の構文と Ebykn の構文が違うとき | `.eyk` では読みやすさを優先。`.eykp` では Verus との近さを優先（LLM の既存知識が効く） |
| Verus の意味論と違えたくなったとき | 違えない。Ebykn は Verus への字句的脱糖で、新しい検証理論は作らない |
| 言葉を選ぶとき | Dafny / Verus / Why3 / Lean / Mezzo / Rust で過半が使う語。「実装の性質」（ghost＝消える）ではなく「意味」（owns＝所有する、spec＝仕様の）を表す語 |
| 健全性のために機能を制限したくなったとき | しない。健全性は目的でない。制限してよいのは「証明の意味が消える」ことを防ぐため（矛盾の lint）だけ |
| 実行時検査を入れたくなったとき | 入れない。利用者が自分で検査関数を書くのは別 |
| Rust から呼べる形を保ちたくなったとき | 保たない（決定 B）。生成 Rust は成果物であって API ではない |
| LLM の作業を楽にするか、人間の読みやすさか | 人間の読みやすさ（`.eyk`）。LLM の楽は `.eykp` 側で |

### 3.3 実装中の迷いの処理
1. 仕様書の該当箇所を読む。書いてあればそれに従う。
2. 書いてなければ §3.1 → §3.2 の順で決め、`OPEN.md` に「何を・どう決めたか・なぜか」を記録する。
3. §5（却下した案）に当たるものは選ばない。
4. 作者に聞くのは、決定が後戻りできず、かつ基準で決まらないときだけ。

## 4. 決定の記録

形式：決定 ／ 理由 ／ 却下した代案 ／ 代償。

### 4.1 思想のレベル
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| 条件付きの正しさだけを保証する | 全依存に証明を付けるのは非現実的。既存資産を捨てるのも嫌う。TypeScript の `.d.ts` と同じ立場 | 全体の健全性／TCB の常時表示／性質の追加を健全性の理由で制限 | 前提が間違えば結論も間違う。受け入れる |
| 性質ファイルは自称でよく、加算的に合成する | 第三者が性質を足せないと公共財にならない | `ensures` の追加禁止、`requires` の論理和合成 | 誤った性質が混ざる。多くの人が依存する性質は読まれて直る、という賭け |
| `verified` は依存先の状態を含めて決める | 依存する契約が未証明なのに `verified` と出すのは嘘になる（外部レビュー §7.1） | 関数単位の表示 | 伝播の計算が要る |
| 実行時検査を入れない | 「証明がなければ何が起きても知らない」で揃える（A2） | 証明がない所に検査を挿入、Gradual Verification | — |
| 用語：「条件付き検証」「assumed specification」 | 確立した語 | 「漸進的形式検証」（Gradual Verification と紛らわしい） | — |
| 思想を言語より優先する。言語の普及は目標でない | 作者の目的 | 言語を広めるために性質を PBT に落とす再定式化 | — |

### 4.2 アーキテクチャ
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| Verus ツールチェーン上の構文フロントエンド。字句的脱糖。型・借用・名前解決・証明は rustc / Verus | 独立トランスパイラは「型を知らずに診断する」と「型検査器を自作する」のどちらも取れない。Verus 自身が `verus!` マクロ＋rustc ドライバで同じ構成 | 独立トランスパイラ＋自前の型検査 | 型情報が要る機能（`as` の置き換え、`Vec<絞り込み型>`、線形型の一般化）は段階 2 以降 |
| prelude（Verus クレート）を介して vstd を参照する | vstd の API 名の変化を一か所で吸収 | 生成コードが vstd を直接参照 | prelude の保守 |
| `build/verus` が消去済み Rust クレートを兼ねる | `verus!` が Verus なしでは ghost を消す。別 emitter は不要（OPEN-11） | 独自の消去 emitter | Verus の挙動に依存 |
| 名前解決は限定（クレート索引・依存の interface.json・prelude） | 型推論なしで `uses` / `gives` を持つ関数の呼び出しを書き下すため | 完全な名前解決 | `uses` を持つ関数はパス形か `self.` でしか呼べない（E0514）。実用上は影響が小さい（データ構造のメソッドは `uses` を持たない） |
| `panic = abort` 必須 | unwind 中の権限喪失は「リークだけ」で済まない場合がある（借用中のコンテナ更新） | unwind 許容、既定 abort | unwind を要する用途は段階 2 |

### 4.3 項目とキーワード
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| `fn` / `fn .. = expr`（純粋）/ `spec fn` / `lemma fn` / `unchecked fn` | 全項目が「`fn` ＋ 修飾子」の一つの規則。Leino「pure method は難しく function は易しい」で論理定義を分ける | `def` / `lemma`（`def` は Python / Mojo で関数、`fn` が付かず関数に見えない）、`proof fn`（`proof` がブロック・ファイル・アンカーと重なる）、`logic fn`、実行できる `def` | `lemma fn` は造語。**作者はコードを書いてから変えるかもしれないと明言** |
| `unchecked` 一本 | 一つの逃げ道（A4）。`get_unchecked` の語感 | `trusted`（逆の印象）、`assume fn`、`axiom` | — |
| `spec fn` の既定は open、`closed` で隠す | Dafny は透明が既定。初学者に優しい | Verus と同じく明示必須 | 非公開のものを参照する `pub open` は Verus がエラー。`closed` を付ける |
| 純粋関数は同じ式を `fn` と `spec fn` に書き下す | Dafny の `function`、MoonBit の `#proof_pure` | 別々に書く | 式が両モードで妥当である必要 |
| `decreases`：`spec fn` の再帰は必須、実行関数は任意 | 条件付きの立場では停止性は選べる性質。定義の整合性には要る | 全て必須 | — |
| `#[test]` は `unchecked` | テストは実行して確かめるもの | — | — |

### 4.4 契約と論理式
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| 句は `uses` / `gives` / `requires` / `ensures` / `returns` / `decreases` / `no_panic`。シグネチャの後、本体の前 | Verus と同じ語と位置。重要度の低い長い部分は後ろ | 属性形 `#[requires(..)]`（Creusot / Prusti） | — |
| `forall x: T, P`、`forall x in r, P` | Verus の `forall\|x\| ..` より読みやすい。脱糖は機械的 | Verus 形のまま | 束縛子の読み方の規則が要る |
| `and { }` / `or { }`（式） | 複数行の不変条件は `&&` で繋ぐと読めない。Verus の `&&&` は記号を増やす | `&&` のみ、`&&&` | 造語 |
| `==>`、`<==>` | Verus と同じ | `implies` 等の語 | — |
| `old(x)`、`final(x)` | Verus と同じ。`&mut` を返す関数の契約に `final` が要る（外部レビュー §4.2） | `old` だけ | — |
| view は明示 `v.view()`。実行 API 名は論理文脈で対応する論理関数に解決 | 暗黙の全面変換は「`s.len()` が文脈で違う値」のような予測不能を生む（外部レビュー §5）。Verus の `when_used_as_spec` が同じ仕組み | 暗黙 view（0.2 の決定）、`v@`（`@` の意味が増える）、`model(v)`（トレイト名と不一致） | — |
| `==` は意味上の等しさ。`=~=` は `.eykp` のみ | 契約は意味を書く。拡張等価は証明の道具 | 契約でも `=~=` | — |
| `no_panic` → Verus `no_unwind` | Verus の unwind 解析は panic 経路の追跡そのもので、abort 下でも符号化として正しい | 独自の解析 | 語が「unwind」でないので説明が要る |
| トリガは `.eykp` のみ。Verus の `#[trigger]` 形 | 契約に証明の都合を混ぜない。`.eykp` は写しなので契約にも付けられる。Why3 の `[t]` は `r[p]` と、Dafny の `{: }` は `and { }` と衝突。属性形は Rust の組み込み属性（`#[inline]` 等）に先例 | ソースにも `#[trigger]`、Why3 形、Dafny 形、独自のアンカー記法 | 組み込み属性がユーザー属性マクロと別物なのは「気持ち悪いが許容」（作者） |

### 4.5 権限と資源
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| 権限は変数に結び付く `p@`。読み書きは `*p` | 関数呼び出しの形（Verus）を無くす。Mezzo の `x @ t` | `@own(p)` 等のトークン表記、`pts[p]`、`Own<p>` | `p@` が生きている間は `p` に再代入・シャドウ不可 |
| `take r[p];` / `put r[p];`（名前なし） | `p` の権限は常に `p@`。別名 `t` は Verus の API を写しただけで不要（作者の指摘） | `let t = take r[p];`、`put r[p] = p@;` | — |
| `[]` を領域の添字に | `HashMap` の鍵参照と同じ「鍵で開ける」読み（作者） | `r@p`、`r.at(p)`、Mezzo の `take p from r` / `give p to r` | 論理文脈では値、実行文脈では場所、という Rust と同じ二重性 |
| `borrow r[p] { }` ブロックのみ | 寿命が見える。文形は必要になったら足す | 文形 `borrow r[p];` | — |
| `borrow mut` は `remove` ＋ `insert` に脱糖 | `tracked_borrow_mut` の有無に依存しない | `tracked_borrow_mut` | — |
| 集合からの取り出し・分割・戻しは明示 | 字句的脱糖で流れ解析をしないため。暗黙化は隠れた制御フロー（A5） | `@open(&self@nodes)`（以降暗黙に借りられる） | Verus と同じ量の操作。減るのは見た目と証明の混在 |
| `owns { }`（権限）と `spec { }`（抽象状態）の二節 | 規則が違う（線形か複製自由か）。`owns` に `Seq` を入れるのは語義がずれる（作者）。`spec fn` と同じ語 | 一節 `owns`、一節 `@ { }`、`erased { }`（ghost と同じ理由で不可）、`model { }`（`View` と重なる）、`tracked { }` | **作者は「記述が邪魔なら一節にする別の語を後で検討してよい」と明言** |
| `self@x` で消去フィールドを参照 | 実行時フィールド `self.x` と形を分ける（違うものに違う形） | `self.x`（宣言で一度印を付ければ使用箇所は不要、という `pub` の類推） | — |
| 実行時の値は `( )`、消去される値は `uses` | 位置が印になる。型名に `@` を付けなくてよい | `heap: &mut Heap<T>` を引数に、`@Region<T>` 型 | — |
| `uses p@`（移動）/ `uses &mut p@` / `uses &p@` / `gives r@` | Rust の引数モードと同形 | Mezzo の `consumes` | 造語 |
| `Ptr<T>`、`Cell<T>`、`Region<L>`、`PointsTo<T>` | Ebykn の表層にポインタは一種類（修飾不要）。Region は Tofte–Talpin / Cyclone / Mezzo の adoption の概念。`PointsTo` は分離論理の語 | `PPtr` / `PCell`（Verus）、`Heap` / `CellPerms`（造語）、`Loc`、`Arena`（割当戦略を連想）、`Slot` | `Cell` は std と同名（OPEN-2） |
| `Ptr::new(v)` / `p.free()` / `Ptr::empty()` | `Box::new` / `Box::into_inner` と同形。Rust 自身が `box` キーワードを捨てた | `alloc(v)` / `free(p)`、`box` 風キーワード | その場構築の保証なし（Rust の in-place initialization に追従） |
| 構造体リテラル・パターンで `@name: ..` | `self@name` と同じ印 | 別節、既定値 | — |
| `*c` でセルの中身を読み書き | `Ptr` と同じ規則（スコープで決まる） | `c.get()` / `c.set()` | `Rc<Cell<T>>` の Rust デリファレンスと見た目が同じで意味が違う。**実例で確認する** |
| 権限の線形性は構文的に検査（Austral の検査器と同程度） | 型なしでできる範囲 | Verus の affine に任せる | クロージャは権限を捕捉できない |
| 自己参照構造体は対象外 | フィールド単位の権限と移動不能性が要る | — | — |

### 4.6 型不変条件と絞り込み
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| `impl Invariant for T { spec fn invariant(&self) -> bool = ..; }` | 型についての関数はトレイト。Creusot の先例 | `struct T { } invariant { }` 節（ループの `invariant` と同語が別位置）、`impl T { invariant = ..; }` | — |
| 契約への展開（Dafny `{:autocontracts}`、Boogie 方法論） | 本体の途中で破れる。字句的 | Verus `type_invariant`（代入直後の成立を要求し普通のコードが書けない）、Spec# の `expose` ブロック（全 `&mut self` メソッドがノイズ） | `pub` メソッドの途中で `pub` メソッドを `self` に呼ぶときは成立を示す。`&mut` フィールドを返す関数は書けない |
| 非 `pub` には足さない | 補助関数で部分的な更新を分けるため（Dafny と同じ） | 全メソッド | 非 `pub` には保証なし |
| 入れ子の不変条件を自動で含める（Creusot 方式） | 書き忘れがない。「フィールドの型の契約はそのまま使える」感覚 | Dafny 方式（明示） | 含めたくない中間状態の型に逃げ道が要るかもしれない。**作者は「使ってみて必要なら考える」と明言** |
| 部分集合型 `type T = B where P(self);` を別に持つ | 「表現不変条件」（型が生涯維持する）と「値の選別」（有限なメッシュ）は別物。後者をラッパー型にすると組み合わせの数だけ型が増える（作者の指摘） | 性質ごとのラッパー型 | 検証する呼び出し側にだけ効く。rustc に弾かせたいならラッパー |
| `where` を使う | 述語は値の集合を絞る制約で、Rust の `where` と同じ役割。`requires` は引数位置以外で意味が変わる | `requires` を型に付ける、Dafny の `\|`、F\* のインライン形 | Rust の where 句との曖昧さ解消規則 |
| 組み合わせは `where` の中の連言 | 一つの書き方 | 交差記法 `A & B` | — |
| 展開位置は直接・`&`・`&mut`・`Option`・`Result` | 型検査なしで字句的に展開できる範囲 | 全位置 | `Vec<T>` 等は手で書く |

### 4.7 実装・契約と証明の分離
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| 二重ファイル：`src/*.eyk` と `proof/*.eykp`（写し＋証明） | ソースを読む人は証明を見ない。証明の `git diff` が文脈つきで読める。ソース追従は 3-way merge（git 標準）。Verus と同じ形で LLM の知識が効く。「写しは二重管理」という懸念は過剰だった（スナップショット vs パッチの違いしかない） | 単一ファイル＋折り畳み、ソースにラベル＋専用 diff（ラベルはソースへの漏れ）、アンカー付きサイドカー（独自のあいまい一致、合成ビューが要る）、単一ファイル＋git textconv（GitHub で見えない） | 実装だけ変えた PR で証明側に写しの更新が出る（自動） |
| 一致検査は基準版（`--base`）と比較 | 剥がして一致、だけでは両方同時に弱められれば通る（外部レビュー §8） | 現在の両ファイルの比較だけ | — |
| 別ディレクトリ（`src/` と `proof/`） | 実装を読む人と証明を読む人で見たいファイルが完全に分かれる。`.eykp` は写しを含むので隣に `.eyk` は要らない（作者の指摘） | 同じディレクトリに別拡張子で隣接 | ミラー構造の維持（ツールが検査） |
| 拡張子 `.eyk` / `.eykp` | MoonBit の `.mbt` / `.mbtp`。登録なし。ハイライトを変えられる | `.ebykn`（長い） | — |
| ソースには証明構文を**文法上**書けない | 読む人に証明が見えないことを文法で保証 | lint | — |
| ループ不変条件は両方に書ける。証明側は追加のみ | 不変条件は設計でもあり証明でもある。追加は契約を弱めない | ソースのみ、証明のみ | — |
| 証明フェーズはソースを変えられない。変更は提案として出す | 証明を通すために契約を弱めたりアルゴリズムを壊したりすることを防ぐ。実装側がレビューして取り込む | 証明エージェントがソースも編集 | — |

### 4.8 性質ファイルとエコシステム
| 決定 | 理由 | 却下した代案 | 代償 |
| --- | --- | --- | --- |
| `props <crate> = "<版範囲>";` ヘッダ、`unchecked fn path::f(..)` | Verus の `assume_specification` に版と合成を足す | — | — |
| `ensures` は加算、`requires` は追加不可、`#[override]` は明示 | 加算は呼び出し側の義務を変えない。`requires` の追加は他の利用者を壊す | 上書きのみ、`requires` の論理和 | `override` 後は依存する証明を unverified に戻す |
| 配布は crates.io の `<crate>-props`、正は中央モノレポ | PEP 561 の `foo-stubs`。DefinitelyTyped / typeshed / Liquid Haskell は中央に収束した | 分散パッケージのみ | — |
| 対象を包まない外付け | Liquid Haskell の wrapper パッケージ方式は煩雑で撤回された | wrapper | — |
| 矛盾の lint（任意） | 矛盾した前提は証明を無意味にする。健全性のためではない | 強制 | — |
| 公開境界は閉じる（B） | `requires` 付きを safe API にはできない。既存 Rust への導入は `main` を Ebykn にして呼ぶ側から移す。TypeScript が広まった今 JS から TS を呼ぶ需要は小さい（作者） | Rust から呼べることを要件に（A）、項目ごとの export（C） | 安全網：`requires` 付き `pub fn` は生成 Rust で `unsafe fn` |

### 4.9 ツールと工程
| 決定 | 理由 |
| --- | --- |
| 段階 0 で Verus を使い込み、prelude を先に書く（M0） | vstd の API 名を確定し、Drop・`?`・`for` の対応を確認してから脱糖を書く |
| 段階 1b で「Ebykn 構文と Verus の差」を手作業で測る | 差がキーワード置換程度なら言語を作る価値が薄い（go/no-go） |
| 構文解析器は `syn_verus` フォークから | 速さ。手書き（LunarML・rustc・Swift・Elm の経験則）は診断の質が問題になってから |
| 整形器 `fmt` は段階 2 | gofmt のように構文の見た目の議論を整形器で終わらせる方針は維持 |

### 4.10 名前
Ebykn で確定。設計中のリポジトリは `ebykn-proto`、公開時に改名。由来は「エビやカニ」（Rust の甲殻類）。「えびやかに」と書くと「えびやか」という形容動詞があるかのように見える言葉遊び。これは裏設定で、表向きの読みは自由（エビキン、エビケン、イービーワイケーエヌ、何でもよい）。

## 5. 却下した案（再提案しない）

| 却下した案 | 理由 |
| --- | --- |
| 言語を安全度で層に分ける（safe / unsafe 的な 3 層） | 「この方針には一切合意できない」（作者）。区分は verified と `unchecked` の 2 つだけ |
| 証明がないときに実行時検査を挿入する | 「証明がない場合は何が起きても知らない」で揃える |
| 全体の健全性を目的にする。TCB の常時表示。性質の追加を健全性の理由で制限する | 思想に反する |
| 「漸進的形式検証」という語 | Gradual Verification（実行時検査で埋める研究分野）と紛らわしい |
| `trusted` の語 | 「信頼できる」と読めて逆の印象 |
| `ghost` の語（キーワード・修飾子・ブロック・節） | 「実行時に消える」という実装の性質しか表さず、意味を表さない。`erased` も同じ理由で不可 |
| 用語の増殖（`pending`、`axiom`、`assumed` / `derived` / `proved`、`maintains`、`show`、`apply`、`have`） | 状態はツールが verified / unverified と表示するだけ |
| `logic fn`、実行できる `def ... by { }`、`@f()` の補題呼び出し、`v@` の view、ヘッダ `proof {}`、`auto lemma` | 一貫性・読みやすさ・先例の不在 |
| 資源を印なしのフィールド `nodes: Heap<..>` として書く | 実行時のフィールドに見える。「全然違う意味のものを同じ書き方にまとめるのはよくない」 |
| `pts[]` / `pts()` / `[\|p\|]` などトークンの括弧表記 | 添字・呼び出しに見える |
| 同じ `proof` 名で 2 種類のブロックを表す | 違うものに同じ形を与えない |
| `@open(&self@nodes)`（以降暗黙に借りられる） | 隠れた制御フロー。`contains` の義務が見えない |
| 暗黙 view（`v.len()` が文脈で `int` になる） | 予測不能（`s.len()` のバイト長問題） |
| ラベル付き証明ファイル（ソースにラベルを足して証明側から参照） | ラベルは証明の都合がソースに漏れたもの。`git diff` で `src/` に差分が出る |
| アンカー付きサイドカー（写しなしで証明だけを貼る） | 独自のあいまい一致の実装、合成ビューが要る、`git diff` で文脈が読めない。「写しは二重管理」という懸念は過剰だった |
| 単一ファイル＋git textconv | GitHub の PR 画面では見えない |
| 性質ファイルの第一消費者を PBT やテストにする再定式化 | 「自分の書いた部分だけ性質の証明されたコードが書ける世界観」が本体。普及のために思想を弱めない |
| Rust から呼べることを設計要件にする | §4.8 |
| 性質ごとのラッパー型（`FiniteMesh(Mesh)`） | 組み合わせの数だけ型が増え、入れ子の順序が問題になる。部分集合型で置き換え |
| `owns { }` に抽象状態（`Seq`）を入れる | 語義がずれる。`spec { }` に分けた |
| `Heap<T>` / `CellPerms<T>` の名 | 造語で、概念の確立した語（region）がある |
| `alloc(v)` / `free(p)` の自由関数 | `Ptr::new` / `p.free()` が Rust の慣習 |
| `let t = take h[p]` / `put h[p] = p@` | 別名は不要 |
| 領域を実行時引数の位置に書く（`heap: &mut Heap<T>`） | 消去される値は `uses` に |
| `model(v)` | `v.view()` に |
| `impl T { invariant = ..; }` | トレイト形に |
| Verus `type_invariant` への脱糖 | 代入直後の成立を要求し、普通のコードが書けない |
| ソースへの `#[trigger]` | 証明の都合を契約に混ぜない |
| Why3 形 `forall x [t], P`、Dafny 形 `{:trigger}` | `r[p]`、`and { }` と衝突 |
| 独立トランスパイラ＋自前の型検査 | §4.2 |
| 「8 本の記事を読めば十分」という解釈 | 広く信頼できる専門家の一次資料を集めて読む |

## 7. 既知のリスクと、未検証の前提

### 7.1 リスク
| # | リスク | 対処 |
| --- | --- | --- |
| K1 | 権限構文が Verus より有意に読みやすくならない | 段階 1b で測る。否なら C2・C3 をツールとして残し、言語は作らない |
| K2 | Verus 依存（pre-1.0、nightly 固定、構文の変化、Drop・async・可変捕捉の未対応） | 版の固定、prelude での吸収、上流貢献 |
| K3 | 型不変条件の展開が実例で通らない（`pub` から `pub` を呼ぶ制約） | 補助関数の切り出し。`expose` を足す |
| K4 | 性質ファイルが 1 人の `assume_specification` 集に留まる | 思想の提示が目標。実例一つで足りる |
| K5 | E0514（`uses` 関数のメソッド呼び出し不可）が実用で邪魔になる | 段階 2 で名前解決を広げる |
| K6 | 作業量 | マイルストーンごとに止められる構成 |

### 7.2 M0 で確認する Verus の前提
- vstd `simple_pptr`：`PPtr::new` / `empty` / `borrow` / `write` / `borrow_mut`（`final` 付き）/ `into_inner` の名前と契約。
- vstd `cell::PCell` の同等 API。
- tracked `Map`：`tracked_insert` / `tracked_remove` / `tracked_borrow`。
- `#[verifier::when_used_as_spec]` と純粋関数の対。
- `assume_specification` が同一関数への重複宣言を拒むこと。
- `broadcast group` / `broadcast use`。
- `no_unwind`、`by(bit_vector)` 等の 5 モード、`#[verifier::opaque]` / `rlimit` / `spinoff_prover` / `memoize`。
- ユーザー定義 `Drop`、`?`、`for .. in` の `invariant`、`let-else`、クロージャの対応状況。
- `verus!` が Verus なしの rustc で ghost を消去してビルドできること。
- 検証結果の JSON 出力の有無。
- 浮動小数点：`is_finite_spec` 等のビット述語のみ、演算は未解釈。

### 7.3 設計で依拠した外部の事実（変わりうる）
- Rust `core::contracts` は nightly の実験（#128044）で、エディションに結び付かず安定化予定なし。実行可能な述語で論理は書けない。
- verify-rust-std は std のみ・UB 不在のみ。Verus・Creusot は審査中。
- Rust Project Goals は「契約言語の統一はスコープ外」。
- Rust の in-place initialization は 2025H2 の Project Goal で提案選定中。

## 8. 用語

### 8.1 使う語
| 語 | 意味 |
| --- | --- |
| 条件付きの正しさ | `unchecked` が正しければ verified は正しい |
| assumed specification / `unchecked` | 自称する性質 |
| verified / unverified | ツールの表示。依存先を含めて決まる |
| 権限 / 領域 / 仕様の世界 / `@` | `PointsTo` / `Region` / 実行時に存在しないもの / その印 |
| 絞り込み | 部分集合型と型不変条件の総称 |
| source / proof / props | `.eyk` / `.eykp` / 性質ファイル |
| 表現不変条件 | 型が生涯維持する内部整合性（`impl Invariant`） |

### 8.2 使わない語
`ghost`、`trusted`、`漸進的形式検証`、`TCB`（表示の意味で）、`erased`（キーワードとして）、`Heap` / `CellPerms`、`model(v)`、`def`、`alloc` / `free`（自由関数として）。

## 9. AI との分担の想定

| 役割 | 編集できるもの | 検査 |
| --- | --- | --- |
| 実装（人間＋AI） | `src/*.eyk`、`props/` | `ebykn check`、`verify` |
| 証明（主に AI） | `proof/*.eykp` のみ | `ebykn check --base <rev>`：`src/` が基準と一致しなければ失敗。証明を通すのに `src/` の変更が要ると判断したら、変更せずに提案（`proposals/`）として書く |
