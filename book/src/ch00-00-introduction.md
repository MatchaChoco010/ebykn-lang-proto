# はじめに

Ebykn は、Rust にトランスパイルして Verus で検証する言語です。信頼しているライブラリが自称する性質を前提に置き、自分が書いた部分だけを、選んだ性質について証明します。

## Ebykn とは何か

形式検証は、これまでプログラム全体の正しさを証明することを目標にしてきました。しかし多くのソフトウェアにはそこまでは要りません。開発者は標準ライブラリや広く使われるライブラリを信頼し、自分が書いた部分だけをテストで確かめてきました。Ebykn は、この「信頼の上で自分の部分を確かめる」作業を、テストから証明へ引き上げるための言語です。

Ebykn が引き受けることは三つです。

- **権限を構文で書く。** `Ptr<T>` の読み書きを `*p` と書き、`unsafe` なしで連結リスト・グラフ・内部可変性を書けます。検証が通れば未定義動作はありません。
- **実装・契約と証明を分ける。** 人が読む実装と契約は `.eyk` に、主に AI が書く証明は `.eykp` に置きます。`.eyk` には証明を文法上書けません。証明を足すときに実装と契約が変わっていないことは、ツールが機械的に検査します。
- **性質ファイルを共有する。** TypeScript の `.d.ts` がライブラリの型を自称するように、性質ファイルはライブラリの性質を自称します。証明されていなくても構いません。

型・借用・名前解決・証明は rustc と Verus に任せます。Ebykn は Verus の上の構文フロントエンドで、新しい検証理論は作りません。

## 何を保証し、何を保証しないか

Ebykn が保証するのは次の一文だけです。

> `unchecked` の印が付いた主張（自分のコードの検証しない部分、性質ファイルの宣言、公理）がすべて正しければ、verified なコードは未定義動作を起こさず、宣言した契約を満たす。

次のものは保証しません。

| 保証しない | 理由 |
| --- | --- |
| `unchecked` の主張が正しいこと | 前提として受け入れる。`.d.ts` が実装の型を保証しないのと同じ |
| プログラム全体の健全性 | 目的にしない。すべての依存に証明を付けるのは現実的でない |
| 証明がない箇所の実行時の挙動 | 実行時検査は挿入しない。証明がなければ何も保証しない |

各項目の状態はツールが表示します。

- **verified**：本体の証明が通り、依存する契約がすべて verified か `unchecked`。
- **unverified**：証明が未完成か、依存先に unverified がある。
- **unchecked**：主張だけで、検証していない。

`ebykn status` は、自分の結論が何を前提にしているかを一覧にします。次にどこを証明すればよいかを知るための地図です。

## この本の読み方

この本は *The Rust Programming Language* に倣った章立てで、Rust を書ける読者を想定します。Rust と同じところは説明せず、Ebykn で変わるところだけを書きます。

- 「入門」で道具を入れ、小さなスタックを書いて検証します。
- 「契約を書く」で、契約・権限・領域・型不変条件を順に学びます。ここまでは `.eyk` だけを書きます。
- 「証明と前提」で、`.eykp` の証明、性質ファイル、`ebykn status` を扱います。
- 「実例」は、双方向リストや glTF の検証など、まとまったプログラムです。

本の中のコード例は、すべて CI で `ebykn` にかけて確かめます。例の種類は次の五つです。

| フェンス | 意味 |
| --- | --- |
| `eyk check` | `ebykn check` が通る |
| `eyk verify` | `ebykn verify` が通る。直後の `status` ブロックが期待する結果 |
| `eyk fail` | 直後の `diag` ブロックの診断で失敗する |
| `eyk skip` | 実行しない。1 行目に理由と追跡 Issue がある |
| `console` | コマンドの実行例 |

言語の規範はリポジトリの `docs/ebykn-spec.md`（実装仕様）、考え方は `docs/ebykn-thesis.md`（思想）にあります。この本と食い違うときは仕様が正しく、本の誤りです。
